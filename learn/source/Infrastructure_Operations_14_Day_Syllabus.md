# Administration & Technical Configuration for Infrastructure Operations Freshers (Linux, Windows Server, AWS, Nutanix, Networking, Security, ITSM & Automation)

**Duration:** 14 intensive training days (approximately 98–112 hours, at 7–8 hours per day)  
**Training approach:** Accelerated foundation and operational readiness, with hands-on labs, verification evidence, controlled troubleshooting, and integrated operations practice.  
**Scope:** Coverage of the original Day 1–11 Linux/AWS syllabus plus Windows Server, RHEL, S3 backup/DR, HPE/iLO, Nutanix AOS/AHV/Prism, HYCU, enterprise networking, FortiGate, BIG-IP, centralized logging, ServiceNow, PalletControl, privileged access, IAM audit, and operations automation.

## 1. Orientation & Linux Administration Foundations

### 1.1. Day 1

- Concept/Lecture: Infrastructure administration roles and responsibilities, L1/L2 support boundaries, operational safety, production and non-production environment separation, change authorization, least-privilege principles, standard operating procedures, runbooks, incident escalation, access management, configuration baselines, asset inventory, audit evidence, and lab readiness; Linux architecture, kernel, shell, distributions, Red Hat Enterprise Linux (RHEL) and other Linux distributions, filesystem hierarchy, CLI navigation, absolute and relative paths, file and directory operations, command syntax, pipes, redirection, command history, help utilities, safe command execution, users and groups, ownership, file permissions, chmod/chown/chgrp, umask, sudo, SSH authentication, SSH key management, and secure administrative access.
- Assignment/Lab: Prepare the administrative workstation, approved access checklist, Linux/RHEL lab environment, evidence repository, and personal learning baseline; perform CLI navigation, file creation, copying, moving, deletion, searching, and text-processing exercises; create and manage controlled users and groups, configure ownership and permissions, establish least-privilege sudo access, generate and configure SSH keys, verify authorized and denied access, document executed commands, and submit system inventory, access verification, and configuration evidence.

#### Additive skill coverage — Evidence handling and operational baseline

- Additional Concept/Lecture: Define an evidence ID, source owner, hostname/asset ID, environment, collection time with timezone, query/window, collector, ticket reference, file size, record count, SHA-256 and storage/access classification. Separate untouched source exports from working copies and redacted deliverables. A hash detects changes against a trusted recorded baseline; it does not by itself prove source authenticity or completeness.
- Additional Assignment/Lab: Create the shared evidence manifest and operating checklist used throughout all 14 days; hash a sample export, alter a working copy, detect the mismatch, and record the transformation without replacing the original.
- Acceptance/Evidence: A reviewer can trace one evidence item to its source and ticket; originals remain unchanged and the modified copy fails comparison against the original hash.

### Delivery & Scope Notes

## D. Common evidence and automation acceptance contract

### D.1. Evidence manifest and traceability

Each submitted evidence item contains: evidence ID; source system/product/version; environment/asset/account identifier as appropriate; related ticket and stable record key; collector; collection timestamp/timezone; requested time interval and exact filters/commands; export format/encoding; file path/name, size, count and SHA-256; access/retention classification; parent evidence ID and transformation/script version for derived files; and limitations/errors. For ServiceNow exports, retain stable IDs where authorized and document display-value versus internal-value handling. Export only the fields and attachments within the approved scope.

Preserve an untouched raw export and process a copy. Verify hashes after transfer and before analysis; use counts and known events to check completeness. Redacted copies get their own hashes and a redaction note. Do not claim that a matching hash proves the source was truthful, the selected time window was complete or the query was correct. Screenshots supplement exportable records rather than replacing them without explanation. If retention, permissions, collection failures or unsupported fields prevent complete extraction, record an evidence gap and obtain the reviewer's decision.

### D.2. Minimum automation test catalog

| Test group               | Required cases                                                                                                           | Acceptance                                                                                                                                                  |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Identity matching        | Leading zeros, long IDs, whitespace/case rules, duplicates, missing owners, cross-system ID collisions                   | No accidental numeric conversion or silent many-to-many join; deterministic exceptions match the answer key                                                 |
| File/encoding            | UTF-8 with/without BOM, UTF-16, supplied CP932 fixtures, quotes, delimiters, embedded newlines, CRLF/LF, malformed bytes | Explicit input/output contract; expected text survives round-trip; unmappable/malformed data is rejected or quarantined with a reason                       |
| File/process failure     | Missing/locked file, permission denied, empty input, missing header, path with spaces, child-script failure              | Observable failure/exit status, useful sanitized log and no misleading success output                                                                       |
| IAM boundaries           | Before/on/after review cutoff, new account, absent last-use evidence, service/break-glass account, stale approval        | Policy-specific expected result and evidence gap recorded; no automatic revocation based only on missing data                                               |
| API/network/TLS          | 401/403, timeout, server-error fixture, malformed JSON, invalid certificate, unhealthy member                            | Bounded execution, TLS verification retained, explicit failed assertion and sanitized diagnostics                                                           |
| Password generation      | Policy length/character requirements, invalid policy, secure random provider failure, secret leakage check               | Approved secure generator and fail-closed handling; no plaintext secrets in workbook/report/log; uniqueness sampling is not proof of cryptographic security |
| Outlook/report           | Missing folder/attachment, duplicate filename, disallowed attachment path/type, unavailable profile                      | Controlled test mailbox, safe attachment handling, draft/attachment checks and no automatic send                                                            |
| Repeatability/regression | Same inputs twice, unchanged reference cases, modified input, partial prior output                                       | Stable business results, no duplicate side effects, preserved inputs/reviewer decisions and traceable new run ID                                            |

Tests use a trusted expected-output dataset or independently reviewed assertions, not just comparison of a program against itself. Record case ID, requirement, fixture version, expected result, actual result, pass/fail, defect/ticket and retest status. A failed case cannot be relabelled passed because the script completed. Mask secrets in error paths as well as successful paths.

### D.3. Completion rubric and gaps

For every matrix row, record **H** (learner executed on actual product lab), **S** (learner executed with simulation/fixtures), **D** (instructor demonstration only), or **T** (theory/reference only), plus assisted/independent status, evidence ID, assessment outcome and reviewer. Target H for core server, AWS, automation and accessible product tasks; S is an explicit fallback for unavailable enterprise products. D/T exposure does not count as completed hands-on experience. Mark edition-specific Windows and version-specific product coverage separately.

Completion requires all original assignments accounted for, every requested skill row mapped to evidence or an explicit access/practice gap, all mandatory acceptance checks passed on the available lab/fixtures, and all seeded critical faults found or correctly escalated. Unknown production facts must remain unknown. Missing privileged-access revocation proof, backup restore verification, critical automation tests or integrity checks remain open gaps. A mentor signs the scoped outcome and assigns owner/action for each gap; completion of the course does not erase unperformed hands-on work.
